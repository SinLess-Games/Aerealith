## Architecture and configuration

The default model has **316,720,128 trainable parameters**, verified from actual
module parameters on the meta device and checked against the analytical formula.
This is 1.30% above the previous 312,656,896 target. It uses 24 layers, hidden width
1,024, 16 query heads, 8 KV heads, RoPE, RMSNorm, causal SDPA, SwiGLU intermediate
width 2,816, residual/pre-normalization, bias-free projections and tied embeddings.
FFN width is approximately eight-thirds of hidden width rounded up to 256, rather
than an arbitrary dimension chosen to reproduce a historical count. Default
context is **8,192**; dropout and gradient checkpointing are configurable.
Additional approximate 500M/750M/1B+ and tiny presets are provided.

Model, tokenizer, preprocessing, tokenization, training, evaluation and generation
have typed validated configurations; unknown keys and invalid numeric settings fail
before expensive jobs. Actual tokenizer vocabulary must match the model.

## Corpus and tokenizer implementation

Supported formats: TXT, Markdown, RST, PDF, CSV/TSV, YAML/YML, JSON,
JSONL/NDJSON, SQL, XML, HTML/HTM, logs and every source/config extension requested,
including extensionless Dockerfile. Readers preserve useful structured keys,
headers, nested records, XML attributes, SQL/code indentation and actual PDF text.
CSV/JSONL/JSON arrays and text stream; structured records/parsers have size limits.
No code/SQL execution, unsafe YAML, OCR, macros or external-reference fetching.

Unicode normalization, trailing whitespace cleanup, empty/short/noisy rejection,
binary rejection, safe parser failures and exact SHA-256 dedup are implemented.
NearDuplicateIndex is an extension contract; a near-dedup algorithm is not yet
implemented. Records use opaque source IDs and content/record IDs. Private SQLite
state maps source IDs to relative filenames; logs exclude document contents.

Tokenizer training/loading uses local Hugging Face Tokenizers byte-level BPE.
PAD/UNK/BOS/EOS IDs are 0/1/2/3; vocabulary and minimum frequency are configurable.
Training samples are capped by default at 256 MiB and 100,000 records. The sample is
a deterministic prefix; use a representative prepared subset for diverse corpora.
Tokenizer inspection reports actual vocabulary, specials and SHA-256 identity.

## Shards, statistics and recovery

Default full shards hold **16,777,216 tokens** in little-endian uint32 binary files:
64 MiB each. Sidecar JSON and SQLite metadata include number, token count, dtype,
checksum, tokenizer identity/version, sequence length, pipeline version and full/
partial status. Reports include documents, records, tokens, full/partial shards,
errors and throughput. Progress events include totals and tokenization ETA.

SQLite WAL/FULL synchronization, output locks, temporary validated files, fsync,
atomic rename and manifest commits protect completed work. Ingestion tracks
fingerprints, size/mtime, status, record/rejection/duplicate counts, checksums,
errors and completion timestamps. Tokenization commits all output shards for each
source together, preserving a recoverable partial tail. Orphan/uncommitted shard
files are ignored and cleaned on resume. Resume verifies checksums and skips
completed work; changed/deleted sources or tokenizer/config changes require an
explicit rebuild. Hashing uses a bounded worker window; parsing/commits are serial.

Recovery granularity is **one source file**. An interrupted large source is retried;
completed sources are preserved. Resume re-reads bytes to verify hashes, without
reparsing/tokenizing completed sources. Tail persistence can add write amplification
for many tiny files; benchmark your corpus and storage before scaling.

`stats` prominently reports unique corpus tokens per actual trainable parameter.
For this model, 20 tokens/parameter needs **6,334,402,560 tokens / 378 full-shard
capacities**; 25 needs **7,918,003,200 tokens / 472 shard capacities**.

## Training, evaluation, checkpoints and inference

The dataset memory-maps binary files, reads sequences across shard boundaries,
keeps a bounded map cache, and supports deterministic multiworker loading. A
constant-memory affine shuffle provides a bijection per epoch. Consumed batch
position is independent of prefetch. Training uses spawned workers.

The actual single-device PyTorch loop includes AdamW, warmup/cosine LR decay,
accumulation, clipping, CUDA BF16/FP16 with a scaler, CPU FP32 fallback, validation,
seed/RNG handling and loss/perplexity, LR, timing, tokens/sec and GPU-memory events.
Effective batch size is batch size times accumulation steps.

Atomic checkpoints contain model, optimizer, scheduler, scaler, step, tokens seen,
consumed batches, Python/NumPy/Torch/CUDA RNG states, configurations, tokenizer and
dataset identities. Loading uses `weights_only=True`. Tests compare interrupted/
resumed training against uninterrupted training with dropout, with exact equality.

Evaluation reports weighted validation loss, perplexity, token count and accuracy.
It rejects directory, shard and normalized-document overlap and requires manifests
for leakage checks. Generation supports greedy decoding, temperature, top-k, top-p,
repetition penalty, seed, EOS stopping and sliding context.

Retriever/RetrievedContext contracts prepare Qdrant or Cloudflare Vectorize adapters
without coupling training/model components to a vector database. Structured numeric
JSON events can feed OpenTelemetry/Prometheus collectors; no new Datadog dependency
was introduced and existing Pyroscope was preserved.

## Failures encountered and corrected

- No dependencies were initially installed. Repository dependencies were installed
  from the existing frozen lockfile; root package.json/pnpm-lock.yaml were unchanged.
- The NixOS host has Node 24.21.0 rather than repository Node 26.5.0. The downloaded
  standalone pinned pnpm could not launch; a temporary pnpm JavaScript CLI was used,
  with version auto-switching disabled. Install runs used pnpm 11.13.1 and 12.3.4;
  subsequent Nx invocations reported pnpm 12.3.4. Nx itself remained pinned at 23.1.1.
- Downloaded Python 3.12 and Ruff binaries could not launch on NixOS. A temporary
  Python copy and the local Ruff executable were adapted to the host ELF loader;
  64-bit C++/zlib libraries were supplied through the environment. These paths and
  adaptations are absent from committed source/configuration.
- Import-order/type errors were corrected. An overly large 335.6M initial FFN
  preset was replaced by the conventional rounded SwiGLU preset. A mistaken expected
  decimal token ratio in a test was corrected without weakening its assertion.
- CLI smoke testing caught an incorrect stats argument attribute and a SQLite
  iterator initialized on the wrong thread; both were fixed and covered by smoke
  testing in the unit suite.
- Existing Cloudflare workerd packages emitted NixOS binary-validation warnings
  during root dependency installation. Their runtime was not changed or tested.

## Remaining limits

Full 138 GB ingestion and production GPU training were not performed. Architecture
counts were checked on a meta model; execution/training were tested with tiny real
CPU models. CUDA paths require suitable wheels/drivers and a production GPU test.
Training is single-device; DDP/FSDP and remote checkpoint stores remain future work.
No KV cache, benchmark suite, OCR/archive support, near-dedup algorithm, RAG storage
adapter or embedding/indexing pipeline is included. Recovery retries the current
source; split enormous sources for finer progress checkpoints. Exact leakage checks
do not detect semantic near duplicates. NixOS needs an appropriate Python/native
runtime environment. The remote CI workflow itself has not been executed locally.

The README provides concrete installation, ingestion, resume, tokenizer, shard,
training, evaluation, inference, extension, storage and troubleshooting commands.
