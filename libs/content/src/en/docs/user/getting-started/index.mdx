# Getting Started

This guide takes you from opening Aerealith to the currently available frontend surfaces. Aerealith is in active foundation development: the repository includes sign-up, sign-in, email-verification, dashboard, and account-screen interfaces, but a configured authentication service is required for those flows to work in a deployment. General-purpose assistant, workflow, module, and integration operation is not yet a demonstrated product capability.

## Before you begin

You need:

- a supported modern browser
- an Aerealith account or an invitation to an enabled deployment
- access to any external service required by your workflow
- a clear description of the task you want to complete

Keep passwords, API keys, recovery codes, private keys, and other secrets outside prompts and uploaded documents unless the feature explicitly provides an approved secure input.

## Start with the account screens

1. Open the Aerealith application.
2. Use [Create an Account](/documentation/user/guides/account/create-an-account) or [Sign In](/documentation/user/guides/account/signing-in) if these routes are enabled in your deployment.
3. Complete [Email Verification](/documentation/user/guides/account/email-verification) when prompted.
4. Confirm that the account shown after sign-in is the one you intend to use.

<SecurityNote>
  Never share credentials, session links, one-time codes, or account-recovery
  information. Aerealith support should not ask you to send these values in a
  prompt or ordinary message.
</SecurityNote>

## Learn the current workspace

The current authenticated shell exposes an overview and account screen. It does not prove that the following planned product areas are available. They may appear in future enabled deployments:

- a conversation or task area
- project context and uploaded material
- connected tools or services
- generated documents, plans, or code
- activity, status, or review information

Read the visible labels and permission prompts before enabling an integration or approving an action. An integration can only work with the access granted to it.

## Use planned capabilities carefully

The following advice applies if an enabled deployment provides an assistant or connected workflow. It is not evidence that the repository currently provides one. Start with a small, verifiable request.

1. State the outcome you want.
2. Include only the context needed to complete it.
3. Describe important constraints, such as format, audience, deadline, or technologies.
4. Review the proposed result.
5. Ask for corrections when assumptions or details are wrong.
6. Verify the final output before using or publishing it.

For example:

> Summarize these project notes into a one-page status update for a nontechnical audience. Separate completed work, current risks, and next actions. Do not invent dates or owners.

This request defines an audience, structure, and factual boundary, making the result easier to evaluate.

## Review before approving

Check:

- names, dates, links, and numerical values
- whether requested constraints were followed
- whether conclusions are supported by the supplied information
- whether an action affects external systems or other people
- whether sensitive information appears in the output

When a task changes files, sends a message, creates an event, or updates an external service, inspect the target and scope before approval.

## If something goes wrong

Try the following:

1. Refresh the page and retry the smallest failing action.
2. Confirm that you are signed into the correct account.
3. Check whether the required integration is connected.
4. Remove unrelated context and restate the desired outcome.
5. Record the page, action, time, and visible error message.

Do not repeatedly submit an action if it could create duplicate messages, events, payments, or records.
